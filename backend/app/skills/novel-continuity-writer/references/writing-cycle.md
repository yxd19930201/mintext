# 创作与续写流程

生命周期服从 `lifecycle.md`。本文件只说明如何把批次任务写成有追读性的草稿。

## 开始条件

先读取：

1. `workflow/state.json`
2. `01-全局设定与创作规则.md`
3. `02-章节滑动摘要.md`
4. `03-当前批次任务.md`
5. `satisfying-structure.md`，起草时只带其中“起草前只记六句话”，全文用于写后去 AI 腔返修
6. 必要时上一章正文

如果没有 active batch，运行 `start-batch`。续写和首创使用同一流程；区别只在于首批没有上一章正文。

正式落草稿前运行：

```powershell
python tools/novel_workflow.py begin-drafting --from-chapter 71 --to-chapter 75
```

## 三层设计

写作前必须能回答：

- 大故事：本批让主角离终极目标更近还是更远？
- 小故事：本批处理哪件具体事件，如何局部结算？
- 单章：每章改变什么，为什么下一章必须读？

回答不出来就先修 `03`，不要用正文试错填字数。

## 批次生产

默认5章，每章2000至3000字。按情节需要可改为3至7章，但一个批次只承担一个主要小故事。

草稿必须独立保存：

```text
drafts/第071章-标题.txt
```

第一行：

```text
第71章 标题
```

每章至少满足：

- 承接一个明确压力；
- 主角有主动目标；
- 阻力有资源、规则或合理判断；
- 出现一次反馈或小结算；
- 结束时信息、资源、关系、风险或位置发生变化；
- 章尾留下危险、选择、期限、收益或揭露。

## 爆款场景构造

优先使用因果链：

```text
欲望 → 具体阻碍 → 合理误判 → 主角选择
    → 反击/失败 → 公开反馈 → 收益 → 新代价
```

爽点不是“主角赢”，而是压力被高倍率结算。不能省略压力、选择、收益或代价。

## 人物写法

- 主角可以狠、俗、嘴欠或好色，但关键选择必须聪明且守边界。
- 反派可以恶，但不能只靠降智送机会。
- 盟友帮助要带条件、成本、误会或立场变化。
- 女性角色有独立欲望、信息和选择；出场必须改变剧情或关系位置。
- 对白使用短句、打断、犹豫、转移和动作，不让所有人说同一种说明文。

## 防水与防 AI 腔

先按 `satisfying-structure.md` 的“四遍去 AI 返修”处理自然度，再做以下检查。不得为了满足结构清单，把已经自然的正文重新改成工整模板。

每写完一个场景检查：

- 删除后是否影响主线、人物或信息？不影响则删。
- 是否连续解释“他知道、他明白、他意识到”？改成动作和反馈。
- 是否只写“震惊、紧张、沉默”？补具体反应。
- 是否重复上一批相同场景、打脸或互动？
- 是否用作者总结代替现场冲突？
- 是否出现“时间地点报幕 + 摆着/放着N样东西 + 连续孤立名词短句”的展品式枚举？物件必须随动作或对话进入现场，不能排队亮相。

## 完成草稿

### 送审前一次扫净

写稿 Agent 完成四遍返修后，必须再做一次**整批预审**。目的不是自评通过，而是在冻结审核基线前把可机械发现、可横向扩散的同类问题一次扫净，避免审核后逐条挤牙膏返修。

动笔前先做“合同可写性审计”：把`03`和五章细纲中的每个字面硬兑现拆成`必须得到的剧情结果 / 指定动作 / 指定载体 / 权限与自愿条件`。若指定动作或载体与程序可信度、人物权限、自愿边界、既有正史或文风自然度冲突，先回到设计层改合同并重新冻结版本；不得一边按旧合同写、一边在正文中用另一套结果替代。

逐项留下可验证结果：

1. **标题与时序**：文件名、首行、`03`、五章细纲逐字一致；标题中的“前、后、两次、十分钟、锁门后”等顺序或数量，必须按正文事件位置真实兑现。
2. **时间口径**：列出本批到场、倒计时、跨夜、行程和伤势时间表；“马上、半小时、十分钟、已经到门口”等说法必须能同时成立。
3. **语义复写**：不只搜索完全相同句，还要检查同章及相邻章是否换词复刻同一种失足撞怀、托腰、敲门、电话打断、湿衣、差吻、围观震惊或证据翻盘。
4. **人物口吻**：成年、自愿、允许和停止权必须清楚，但不能让人物背诵“清醒、自愿、可拒绝”等审核字段；单独朗读对白，必须仍像该人物在谈价、嘴硬、吃醋或试探。
5. **摆拍腔扫描**：搜索`摆了[三四五六七八九十\d]+样`、`放着[三四五六七八九十\d]+`及用于陈列的“第一/第二/第三”；人工检查连续三行以上、每行约十五字以内且缺少有效动作或主语变化的名词短句，并检查所有“时间地点 + 物件清单”开场。删掉数量报幕后若仍像商品展示，就改成物件被拿、压、碰翻、递交或争抢的动态现场；只合并行句不算修复。
6. **权威事实矩阵**：把关键债务、证据、伤势、知识状态和权力来源按`01 / design / 02 / 账本 / 正文`横向核对；发现互斥口径先修权威文件，再生成审核基线。另附两张硬表：
   - 全量物件交接表：枚举正文中每一个有名字的可移动证据物/载体，以及“拿、交、收、锁、导出、拍、打印、夹走、放回、上传、发送”等每一个交接动词；逐件写`来源 → 取得时间 → 有权操作人 → 当前持有人 → 原件/副本 → 实际移交或归还时间与接收人 → 下一公开窗口`。“准备交、让他自己带去、随后留一份”不算完成交接。发现同一事实派生三个以上介质时，先删减或合并，不能靠继续补介质修补介质。
   - 权限动作表：每个锁门、停卡、调监控、取账、盖章、封存、放行、撤权动作都写`执行人 → 原有权限/明确授权 → 可撤销或复核者`；主角提出建议不能自动等于主角有权执行。
7. **修改后全批回归**：任何局部改动都要重新检查标题兑现、事件时序、上下文指代、动作轮换、证据持有链和章尾钩子，不能只复查报告点名的那一句。

预审必须先做“减法检查”：删掉不承担翻盘、知识差、代价或后续钩子的程序物件与交接说明。严谨不是介质越多越好；载体越多，连续性节点越多，返修风险越高。

对“昨夜、今晚、明早、次日、马上、随后”等相对时间词，必须逐个映射到统一时间表；同章跨日后尤其要检查日序称呼。任一项没有证据或仍有冲突，不得运行`submit-review`。预审不能替代独立审核，也不能把自检结论写成审核通过。

草稿齐全后不要直接定稿。运行：

```powershell
python tools/novel_workflow.py submit-review --from-chapter 71 --to-chapter 75
```

脚本验证章号连续、标题存在、正文非空，并把批次转为 `reviewing`。
